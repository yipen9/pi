# task 系列学习文档优化方案

日期：2026-10-11。仓库基线：`ad80850da`。

## 1. 结论与范围

建议先修正文档中影响理解和实验验收的矛盾，再整理阅读路线与公共实验准备，最后逐章调整内容密度。保留现有的具体例子、源码映射、失败路径和离线实验；这些是本系列有用的部分。

本方案针对 `docs/learning/zh-CN/task-00-*.md` 至 `task-16-*.md` 共 17 篇学习文档。两个 `packages/durable` 下的 `task-*.ts` 属于业务源码，不纳入此次文档优化。`epub/` 仅核对文件名与章节对应关系，未检查电子书内部排版。

本次完成全系列的篇幅、标题、时间、导航和实验组织检查，并对基础篇、实验准备、跨章契约和毕业项目作重点内容核对；参数校验与测试 harness 另对照了当前源码。下文区分已发现的问题与建议实施的工作，不代表所有源码结论均已逐行复核，也不代表文档中的实验已重新运行。

## 2. 优先修正：已发现的具体问题

优先级定义：P0 为会教错行为或导致错误验收的问题；P1 为妨碍实验复现和阅读的问题；P2 为维护与发布改进。

### P0-1：参数校验被误写为严格拒绝所有类型不符的输入

**位置：** [第 16 篇「核心概念」](zh-CN/task-16-capstone.md#核心概念)，原第 55 行；对照 [第 06 篇「动手实验」](zh-CN/task-06-tools.md#动手实验) 与 [validateToolArguments 源码](../../packages/ai/src/utils/validation.ts)。

**问题与例子：** 第 16 篇写 `directory: 42` 会校验失败，`execute` 不会运行。第 06 篇却记录了字符串参数接收数字 `123` 后变成 `"123"` 的结果。当前 `validateToolArguments` 在检查前执行 `Value.Convert`，并存在普通 JSON Schema 的转换逻辑。因此不能把“原始输入不是字符串”直接等同于“校验必然失败”。

**方案：** 明确三个步骤：原始参数 → 规范化/转换 → schema 检查 → 执行。成功例同时展示转换后的值；失败例使用不可转换的输入，并通过实际用例确认。若要教授严格拒绝原始类型的业务规则，应另外说明实施位置。

**验收：** 第 06、16 篇对相同 schema 和相同输入给出一致结论；实验记录同时包含原始值、转换值、是否执行。

### P0-2：取消行为在不同章节中不一致

**位置：** [第 06 篇「实验 2」](zh-CN/task-06-tools.md#实验-2观察四类失败的去向设计未在本地运行)，原第 760–775 行；[第 05 篇「实验 4」](zh-CN/task-05-agent-loop.md#实验-4取消的三种情况)，原第 697–774 行。

**问题与例子：** 第 06 篇把取消统一列为 `isError: true`，并说第二次模型请求会收到结果后回复文本。第 05 篇给出的取消轨迹中，工具可以返回 `isError=false`，后续模型流以 `aborted` 结束。读者会把“请求了取消”“工具失败”“后续模型成功回答”混为一谈。

**方案：** 按取消时间点和工具是否配合取消拆表：执行前取消、执行中响应取消、忽略取消后返回。分别记录工具是否执行、工具结果、后续流终态、调用次数和最终空闲状态。第 05 篇负责完整轨迹，第 06 篇链接引用并只解释工具层结果。

**验收：** 相同场景跨章一致；不再把取消一概描述为工具错误或最终文字回答。当前发现是文档间矛盾，最终结论需在修订时按同一版本重跑对应离线场景。

### P0-3：毕业项目对绝对路径的要求矛盾

**位置：** [第 16 篇「实现规格」](zh-CN/task-16-capstone.md#实现规格) 与「评分标准」，原第 274、742 行。

**问题与例子：** 规格用 `resolve(ctx.cwd, directory)` 加根目录包含关系判断。传入根目录内的绝对路径时，这种实现会允许它；评分表却要求“绝对路径被拒”。照着骨架实现可能在评审时被扣分。

**方案：** 推荐统一为“目标必须位于工作目录内，允许根内绝对路径”，与现有实现思路一致；相应修改参数说明和评分表。若另选“只接受相对路径”，则需要在 `resolve` 前增加输入规则，并同步全部例子。

**验收：** 明确列出并覆盖根内相对路径、根内绝对路径、根外绝对路径、`..`、`..foo`、Windows 跨盘符；规格、实现骨架、测试与评分一致。

### P0-4：先红后绿实验不能证明它声称的结论

**位置：** [第 16 篇「设计理由」](zh-CN/task-16-capstone.md#设计理由为什么是两层检查) 与「实验 5」，原第 185、558–569 行。

**问题与例子：** 正文说明字符串检查是可选的快速拒绝手段，`realpath` 仍会检查越界；实验却要求仅删除字符串检查后，`directory: ".."` 的越界用例失败。若真实路径检查仍在且路径存在，工具仍能拒绝，原断言未必失败。

**方案：** 每个故意制造的错误对应一个明确断言：去掉真实路径检查，用根内链接指向根外的固定文件；把精确父目录判断改成 `startsWith("..")`，用合法 `..foo` 检测误拒。若专门验证字符串预检，断言应检查它承诺的提前拒绝行为，而不是重复验证最终是否越界。

**验收：** 正确实现通过；每个指定错误实现都被对应测试稳定检出；移除错误后再次通过。

### P0-5：进程内与进程间协议被混淆

**位置：** [第 15 篇「与主线的对照」](zh-CN/task-15-advanced-systems.md#与主线的对照)，原第 878 行；对照 [第 12 篇「先选入口」](zh-CN/task-12-sdk-rpc.md#先选入口决策表)。

**问题与例子：** 第 15 篇把 task-12 的 JSONL RPC 写为“进程内 RPC”；第 12 篇实际描述宿主与 pi 子进程通过 stdin/stdout 通信。进程内的是 SDK 方法调用。

**方案：** 固定三种表述：SDK＝进程内调用；JSONL RPC＝经子进程标准输入输出通信；CBOR 协议＝按帧传输的远程会话协议。比较传输、消息格式、会话路由与断线处理，不把差别归结为错误的进程边界。

**验收：** 第 01、12、15 篇使用同一组术语和边界定义。

### P1-1：基础代码的展示结果与代码不完全对应

**位置：** [第 00 篇](zh-CN/task-00-typescript-core.md)，原第 221–232、849–864 行。

**问题与例子：** `numbers/total` 示例宣称输出 `total 13 true`，展示的代码却只有函数定义，没有调用与打印。`pick<T extends readonly string[]>(): T[number]` 接受空数组，直接返回 `items[0]`，没有表达空输入可能得到 `undefined`；这也与前面 `first` 练习的教学要求不一致。

**方案：** 可运行示例补齐调用；纯片段标明调用前提。`pick` 要么限制非空元组，要么返回值包含 `undefined`，并展示空数组情形。这里根据所教概念选择一种，避免为解释泛型又引入过多新规则。

**验收：** 复制完整示例可得到所列输出；声明的输入范围与返回结果相符。当前为静态核对，未运行示例。

### P1-2：源码运行约定与毕业实验冲突

**位置：** [第 01 篇「仓库工具」](zh-CN/task-01-orientation.md#仓库工具)；第 16 篇「实验 3」，原第 515–531 行。

**问题与例子：** 第 01 篇提供 PowerShell 启动器 `pi-test.ps1`；第 16 篇却以 `pi-test` 是 Bash 包装为由，要求直接使用已安装的 `pi -e`。读者可能因此加载与当前源码不一致的安装版。

**方案：** 源码学习统一使用仓库启动器；安装版示例单独标明版本和前提。把平台入口集中到公共环境说明，实验仅保留当前命令与工作目录。

**验收：** Windows 与 Bash 的源码路径清楚；不要求读者先安装另一份 pi 才能做本地源码实验。

### P1-3：本机产物被纳入必读仓库地图

**位置：** 第 01 篇「仓库地图」及第 15 篇「15.10 session-backends/sqlite-node」。

**问题与例子：** 两篇把 `packages/session-backends/sqlite-node/dist` 纳入学习内容，第 01 篇还建议读取其中的迁移 SQL。此次 `git ls-files packages/session-backends` 无输出，这不是读者从 Git 检出后必然能获得的资源。

**方案：** 正式地图以受版本控制的包与源码为准。将本机残留目录说明移到环境排障附注；SQLite 学习入口使用第 15 篇已经列出的 `packages/durable/src/storage/sqlite/`。

**验收：** 必做实验和必读路径不依赖未跟踪的构建产物；缺少该目录不被判定为安装错误。

### P1-4：学习计划和章节内引用没有同步

**位置：** 第 01 篇阅读地图、第 13 篇 raw mode 小节、第 16 篇七天计划与测试用例表。

**问题与例子：**

- 第 00 篇页首为 6 小时，阅读地图为 4 小时；第 15 篇分别为 3 与 6 小时；第 16 篇分别为 4–6 与 8 小时。
- 第 13 篇两次引用“实验 10”，实际实验标题只到实验 6。
- 第 16 篇同时使用“两次完成”“七天计划”“七步完成”；七步所列时间合计 340 分钟，正文却说约 5 小时。
- 第 16 篇规格要求 `details` 保存脚本名数组，测试表却允许“完整数量或完整名单二选一”。

**方案：** 分开标记主线阅读、必做实验、选做练习时长；公共索引只维护一份一致信息。实验增加固定标识，如 `T13-L06`。毕业项目统一叫七个里程碑，允许按两次或多次安排；输出字段只保留一套规格。

**验收：** 章节索引与页首一致；每个实验引用都能定位；实现规格、测试表和评分没有不同答案。

## 3. 内容结构优化

### 3.1 为首次阅读和源码查询提供两条路径

现有文档已经包含选读、图和术语表，问题在于主线仍较长，部分资源清单、内部状态与实验设施挤在同一条阅读路径里。

建议新增 `docs/learning/zh-CN/README.md`，提供以下入口，保留现有章节编号：

| 路线 | 阅读顺序 | 完成结果 |
| --- | --- | --- |
| 理解一次请求 | 00 必需语法 → 01 → 02 → 03 → 05 → 06 | 能解释消息如何流动，并运行一个离线工具循环 |
| 开发只读扩展 | 以上基础 → 07 基本生命周期 → 10 → 11 → 14 → 16 | 完成扩展、失败路径测试与评审说明 |
| 会话与上下文 | 07 → 08 → 09 | 区分完整历史、活动分支和下一次模型输入 |
| 集成或专项开发 | 按需读 04、12、13、15 | 能选择 SDK/RPC、供应商入口、TUI 或进阶模块 |

完整顺序阅读仍可使用 00–16；路线入口用于按目的学习。第 15 篇应明确为选修分支，毕业项目不依赖其中全部模块。

### 3.2 每章只保留一个主要问题和一份主讲解释

推荐章节顺序：目标与先修 → 一个具体问题 → 最短正常路径 → 核心概念与源码定位 → 一个必做实验 → 失败路径 → 自测 → 选读 → 下一步。

每个核心小节使用“问题 → 固定输入/短轨迹 → 解决办法 → 为什么需要”的顺序。已有图表若能讲清楚就保留，不为统一格式再加一张同义图。

明确内容归属：

- 第 01 篇主讲环境与仓库入口；第 02 篇主讲完整请求路径。第 01 篇只留简短链路，不再重复详细走读。
- 第 03 篇主讲消息、事件、状态、条目；后续章节用一个短提醒和链接引用。
- 第 04 篇主讲供应商与模型边界；第 14 篇主讲 faux/harness 测试方法；其他章节直接使用统一示例入口。
- 第 07 篇主讲资源生命周期；SDK 篇仅说明调用方必须承担的创建、订阅和释放责任。
- 第 08 篇主讲存储与分支；第 09 篇主讲投影与压缩后的模型输入。

必要的局部解释仍保留，避免读者为理解一句话不断跳转。重复段落只有在解释相同问题、没有提供新行为时才合并。

### 3.3 使用可点击、可离线定位的引用

将纯文件名改成相对 Markdown 链接；跨章定位到实际小节。源码引用同时给出文件与符号，行号只用于本次问题记录，不作为长期唯一入口。

目录中提供上一章、下一章、返回路线和关键词索引。EPUB 导出时将章节链接映射为书内链接；源码链接保留可读路径和符号，不能假定阅读器可访问本地仓库。

## 4. 实验与证据优化

### 4.1 先统一实验准备，再考虑提取代码文件

第一步仅整理公共环境说明：支持的 Node 基线、安装方式、工作目录、源码启动器、指定测试命令、临时目录与清理约定。

第二步再将反复复制的完整实验提取为可维护文件。优先复用现有 examples、harness 和源码解析器；不要再为学习材料维护一套自定义模块加载系统。第 05 篇的三个准备文件是首个试点。

具体实验文件位置须结合根 TypeScript 配置和测试发现规则确定。教程专用代码应避免进入产品包公共 API；进入 `test/suite/` 的测试使用现有 harness 与 faux。此次只提出方案，未新增实验代码。

### 4.2 每个实验统一提供六项信息

| 信息 | 例子 |
| --- | --- |
| 目标 | 证明工具抛错后会生成错误结果，并让模型继续处理 |
| 环境 | shell、cwd、Node、是否需要已安装依赖、是否联网 |
| 输入 | 固定文件内容、固定 faux 响应、固定工具参数 |
| 步骤 | 可复制命令；完整文件入口；需要改动的明确位置 |
| 验收 | 工具调用次数、错误字段、结果内容、流终态，而非只看“没有报错” |
| 收尾 | 本实验创建的文件与释放方式；命令失败时如何清理 |

临时目录使用每次独有的名字，并只清理本次创建的目录。避免固定目录名加 `-Force` 创建，再递归删除整个目录，影响另一个实验进程。

### 4.3 验证记录集中存放，正文保留必要标记

在公共验证记录中记录：实验 ID、仓库 commit、操作系统、shell、Node、命令、退出码、关键结果、未覆盖项。

状态使用明确分类：已实测、源码静态核对、示意骨架、待核对。Windows 上使用 Git Bash 的结果仍归属 Windows，不写成 Linux/macOS 已验证。

正文保留影响读者判断的状态，例如“这是骨架，需补全”；PID、随机路径、逐行警告解释和历史运行日志移到记录中。主线实验至少在声明支持的一个环境中完整跑通，其他平台状态如实记录。

### 4.4 修订毕业项目的验收闭环

推荐按七个里程碑组织：确定契约 → 正常结果 → harness 集成 → 错误映射 → 路径边界 → 错误实现对照 → 评审说明。

关键改进：

1. 将“第 4 天至少三个用例通过”改为“本里程碑要求覆盖的行为全部通过”，明确暂未实现的后续场景。
2. 统一 `details` 字段、`dependencyCount` 统计范围、缺省字段处理、脚本排序与截断规则。
3. 给正常目录、坏 JSON、缺失文件、越界、脚本过多、`..foo`、链接越界分别指定断言。
4. 将“搜索不到 writeFile/exec”改成辅助检查；无匹配不能证明没有写操作或间接副作用。
5. 复用第 11、14 篇的 harness 用法，明确扩展绑定时机；不要让初学者靠猜测补齐公共 API 调用。
6. 说明 `realpath` 检查的边界：它适用于本练习的路径验证，不能据此宣称具备抵御文件系统并发替换的完整沙箱隔离能力。并发替换、超大文件等作为扩展课题，不强行加入基础项目。
